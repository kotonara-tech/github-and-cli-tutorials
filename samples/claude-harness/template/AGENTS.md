# AGENTS.md

このリポジトリで作業する AI エージェント（Claude Code など）向けの手引きです。人間向けの説明は `README.md` にあります。

## プロジェクトの概要

- `todo.sh`: bash で書かれた TODO 管理 CLI。タスクは `TODO_FILE`（既定: `./todo.txt`）に 1 行 1 タスクで保存する（`[ ] 内容` が未完了、`[x] 内容` が完了）
- `tests/test_todo.sh`: テスト。外部のテストフレームワークは使わない

## コマンド

- テスト: `bash tests/test_todo.sh`（最後の行が `結果: N 件成功, 0 件失敗` なら成功）
- 静的解析: `shellcheck todo.sh tests/test_todo.sh`
- コードを変更したら、コミットの前に必ず両方を実行する

## コードの決まり

- macOS 標準の bash 3.2 でも動くように書く（連想配列、`mapfile`、`${var,,}` は使わない）
- `sed -i` は使わない（macOS と Linux で書き方が違う）。ファイルの書き換えは既存の `rewrite_tasks` を使う
- 件数を数えるときは `grep -c` ではなく awk を使う（`grep -c` は 0 件のとき終了コード 1 を返し、`set -e` で止まる）
- `local x=$(...)` とまとめて書かない（shellcheck の SC2155）。`local x` と `x=$(...)` に分ける
- エラーは `die` で表示し、終了コード 1 で終わる
- テストは「準備 → 実行 → 結果の確認」の順に、既存の `reset_todo` / `run_todo` / `assert_equal` / `assert_contains` を使って書く

## TDD の進め方

新しい機能の追加とバグの修正は、テスト駆動開発（TDD）で進める。

1. テストリスト（`TODO.md`）の未チェックの項目を **1 つだけ** 選ぶ
2. Red: その項目のテストを 1 つ書いて実行し、**期待どおりの理由で失敗する** ことを確かめる
3. Green: テストが通る **最小限** のコードを書く（仮実装でもよい）。すべてのテストが通ることを確かめたら、`TODO.md` の項目にチェックを付けて、`feat:` または `fix:` でコミットする
4. Refactor: テストが通る状態を保ったまま、重複や分かりにくい名前を整える。整えたら、`refactor:` として Green とは別にコミットする

- Red でテストが最初から成功したときは、期待値を変えて失敗させない。実装を一時的に壊してテストが失敗することを確かめ、元に戻して（`git diff --stat -- todo.sh` に何も表示されないことを確かめて）、`TODO.md` の項目にチェックを付けて、テストの追加だけを `test:` でコミットする

- テストを消したり、弱めたり（アサーションを減らす、期待値を実際の出力に合わせて書き換える）しない
- 頼まれていない機能を追加しない。気づいたことは `TODO.md` に項目として追加する
- 作業と関係のない不具合を見つけたら、直さずに `TODO.md` の「メモ」に書く

## テストリスト（TODO.md）

- 作業ブランチのリポジトリのルートに置き、コミットする
- 書式: `- [ ] 項目`（未完了）/ `- [x] 項目`（完了）。「メモ」の見出しの下には、TDD の対象ではないことを書く
- Pull Request を作る前に、内容を Pull Request の説明に貼り付け、最後のコミットで `git rm TODO.md` する

## Git の決まり

- `main` に直接コミット・push しない。作業は `feature/<Issue 番号>-<内容>` などのブランチで行う
- コミットメッセージは Conventional Commits 形式で、日本語で書く（例: `feat: stats コマンドを追加`）
- 構造の変更（動作を変えない整理）と振る舞いの変更は、別のコミットにする（`refactor:` と `feat:` / `fix:`）。テストの追加だけのコミットは `test:` にする
- テストと shellcheck がすべて通ってからコミットする
- `git push` と Pull Request の作成は、人間の確認を受けてから行う
